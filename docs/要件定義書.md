## 0. この文書について

「みまもりくん」の要件を、**背景と判断の理由つきで**まとめたもの。これを正本とする。

迷ったときは **第5章「判断の原則」** と **第11章「意思決定ログ」** に戻る。
新しい機能を足すかどうかは、原則に照らして決める。原則に反するものは、便利でも入れない。

## 1. 背景と経緯

### 1.1 どこから始まったか

2026年9月5日、渋谷のミニハッカソンで「自分が本当に困っていることから作る」という課題が出た。
配布シートに困りごとを書き出したところ、**仕事のことは出てこず、家の学校の連絡が出てきた**。

当日中に発想から実装まで通し、撮る → 候補 → 承認 → カレンダー登録までが動いている。

**位置づけ**：「あったら嬉しいやつ」。第5回 Agentic AI Hackathon の本戦（10/15提出）は **okane-kenko のまま**で、こちらに差し替えない。

### 1.2 改名の経緯

当初の名前は「おたより番」。2026-09-05 に **「みまもりくん」** へ改名した。理由は2つ。

1. ウェブクルーの実在アプリ「OTAYORI」と衝突する
2. **売りが「おたよりを整理すること」から「伴走して見届けること」に移った**

名前が変わったのは方向が変わったからであり、この改名自体が製品の芯を示している。

### 1.3 開発体制

ミニハッカソン当日は3人でファイル所有を分けて並行開発した（`分担.md`）。
**その体制は当日限りで終了している。** 以後の編集は単独。

### 1.4 競合を調べてわかったこと

**取り込みの自動化そのものは既に商品**である（コトメモ 月300円・表形式プリントの一括登録に対応済み／TimeTree の予定スキャン／PicCal は無料・アカウント不要）。ここで勝負しない。

**空いているのは3か所。**

1. **複数の子ども × 複数の経路を1本に束ねること**
2. **完了の見届け**
3. **学校のワーク・プリントを載せられる学習計画**（通信教育系は自社教材に閉じていて構造的にやれない）

**紙は当分消えない。** 東京都教育庁も紙とアプリのハイブリッドを前提にしている。

### 1.5 ユーザー（子ども）に聞いた

子ども2人に「あったらいい機能」を聞いたところ、**管理系の要望はひとつも出なかった**。

| 親が欲しかったもの | 子どもが欲しかったもの |
|---|---|
| 漏れないこと | 好きなキャラを調べたい |
| 突合しなくていいこと | 好きなキャラを作りたい |
| 覚えていなくていいこと | がんばったらゲーム時間を延ばしてほしい |
| — | 頑張るモチベーションを作ってほしい |

**親が欲しいのは「漏れないこと」、子が欲しいのは「やる気」。**
"見届ける" の中身は催促ではなく**伴走**だと分かった。

あわせて：子どもは対話型AIの会話がスムーズなので**話したがっている**／ゲーム内通貨を普段から欲しがっている（**報酬の出口はもう手元にある**）。

## 2. 対象ユーザー

### 2.1 親

子ども2人ぶんの連絡を頭で突合して覚えている。やりたいのは「全部を見ること」ではなく「**見なくて済むこと**」。

### 2.2 子ども — 2人で必要なものが違う

| | 下の子（小学校低学年） | 上の子（中学1年） |
|---|---|---|
| 学校外 | 公文式 週2回（英語・国語・算数） | 塾 週2〜3回 |
| 宿題 | プリントが**毎日**。内容は日替わりでない | 学校以外の宿題も多い |
| テスト | — | **9教科が丸ごと範囲** |
| 困りごと | やり切る（続ける） | **学習スケジュールを組むのが大変** |
| 見届けの中身 | *やり切らせる* | *計画を一緒に作って、保つ* |

## 3. 現状（As-Is）と課題

### 3.1 情報が5経路に散らばる

紙のプリント／学校の連絡配信アプリ／親のLINE／学校支給PCの Google Classroom／塾。

### 3.2 通知は来ている。来すぎて沈む

**親が「全部を頭の中で突合して覚えておく係」**になっている。

### 3.3 漏れのコストを払っているのは親ではない

> 漏れる → 参観で言われる → 親が怒る → **子どもが自信をなくす**

つらい瞬間は3つ：情報が散らばっている／丸つけ・見直しの時間／**子どもともめる**。
**切実さの中心はここ**であり、手間の削減ではなく子どもの自己肯定感の話である。

### 3.4 学習スケジュールを組むのが大変（中1）

テスト期間は9教科が同時に走る。課題ごとに独立して計画を立てると、**9本の計画が同じ夜を取り合って破綻する**。

## 4. 目指す状態（To-Be）

| 状態 | 中身 |
|---|---|
| **確認しなくていい安心** | 親が覚えていなくていい。台帳が頭の外にある |
| **明日の持ち物が揃っている** | 前日に、聞かなくても揃う |
| **子どもが自分で回している** | プリントを撮るのは子ども。*親に出す必要そのものを消す* |
| **つまずきだけ見えている** | 全部を見に行かない。例外だけが上がってくる |

- **Before**：親が集める → 親が覚える → 親が催促する → もめる
- **After**：子が撮る → エージェントが束ねて期限を立てる → **完了まで見届ける** → 親は例外だけ見る

## 5. 判断の原則（迷ったらここに戻る）

### P1. 管理アプリではなく「見届ける人」を作る

機能を足すとき、*管理を増やす*方向か*見届けを厚くする*方向かで判断する。

### P2. 読み取りと判断は自律、処置（書き込み）は承認

エージェントは候補を返して止まる。書き込みツールは承認後にしか呼べない経路に置く。
**ただし「何も変えない」判断に承認は要らない**（完全一致のスキップなど。D-33）。

### P3. 価値判断をアプリに持たせない

ポイントの交換レート、教科の優先順位、報酬の中身は、人（親・本人）が決める。
**「提案する」ことはこの原則に反しない。** 決めるのが人であればよい。

### P4. 習慣を壊すものは入れない

毎回のPIN入力、重い手入力、都度の承認 —— 正しく見えても習慣を壊す仕組みは採らない。
**使われないアプリは、機能が正しくてもゼロ点。**

### P5. 連携しない。素材を渡す

学校系サービスのAPI連携は追わない。紙も画面もPDFも「撮る／渡す」に一本化する。

### P6. 出口は既存の生活導線に置く

専用アプリを覚えさせない。予定は Google カレンダーに出し、通知もカレンダーの標準通知を使う。

### P7. 決定的な処理はコード、LLM は入口と出口

配分・再計算・集計はコード。読み取り・説明・会話はLLM。

### P8. 監視ではなく伴走

完了の証跡に写真を必須にしない。計画を変えた本人を否定しない。
**下書きを出したのはこちら、決めたのは本人。**
そして**催促を強めると、怒る役をアプリに移しただけになる**（FR-10 の態度ルールの根拠）。

## 6. スコープ

### 6.1 やること

学校・塾・公文の連絡の取り込み、予定化、日々のタスク提示、完了の見届け、学習スケジュールの下書きと再配分、ポイントと引き換え、相棒との会話、祖父母への写真つきメッセージ。

### 6.2 やらないこと（と理由）

| やらない | 理由 |
|---|---|
| 決済（クレカ紐付け・カード番号の保持） | ゲーム内通貨はコンビニのギフトカードのみ。**月間支出上限はギフトカード引き換えに効かない**ので、カードを持たせないことが唯一の物理的な上限 |
| Google Tasks 連携 | Tasks API は OAuth ユーザー認証必須 |
| 学校系サービスのAPI連携 | 学校支給PCはその端末からしかログインできない（P5） |
| テストの点数との連動 | 報酬は行動に付ける。**Fryer の研究で、点数に報酬を付けた群は改善しなかった** |
| 写真必須の完了確認 | 監視になる（P8） |
| アプリが教科の優先順位を**決める**こと | 価値判断は人が持つ（P3）。提案はする |
| 既存キャラクターそのものの生成 | 権利上の問題。public リポジトリなので特に |
| 兄弟のポイントを並べて比較表示すること | ポイント差は兄弟間の力関係を固定する |
| 相棒が答えを言う／評価する／残りを数える | FR-10.1 の態度ルール |

## 7. 機能要件

### FR-1 取り込み

| ID | 要件 | 根拠 |
|---|---|---|
| FR-1.1 | 子どもがカメラで撮って登録できる（紙／**学校PCの画面**／連絡アプリ／塾のメモ） | 学校の宿題は学校PCに載る。API連携は不可（P5） |
| FR-1.2 | 子どもが**手入力**でも登録できる | PCを開けない日がある |
| FR-1.3 | 手入力は「教科ボタン＋タイトルのみ」「昨日と同じ」で最小化。**1枚10タップ・20秒以内** | 打つのが面倒だと登録されず、虫食いのリストは信用されなくなる（P4） |
| FR-1.4 | 親が `/board` から**ファイルをアップロード**できる（PDF・画像・複数枚・テキスト） | 年間予定表やメール添付は親経由 |
| FR-1.5 | 1ファイルから複数候補が出る場合、一覧＋チェックボックスで一括承認 | 年間予定表は数十件になる |
| FR-1.6 | 候補カードに**原本サムネイル**を並べ、該当箇所に戻れる | AIの結果だけ見せられると確かめようがない |
| FR-1.7 | **一括アンドゥ**（直前の取り込みをまとめて取り消し・10分） | 書いた後の後始末が一番つらい |
| FR-1.8 | 誤読時は**なぞった範囲だけ読み直す** | やり直しが再撮影にならない |
| FR-1.9 | 失敗時のメッセージは**原本のどこを見ればいいか**を指示 | 「読めませんでした」では直しようがない |

### FR-2 正規化・重複・変更の判定

| ID | 要件 |
|---|---|
| FR-2.1 | 相対日付（「あさって」）を実日付に変換 |
| FR-2.2 | どちらの子どもか判定し、**確認ステップでデフォルト選択値として出す** |
| FR-2.3 | 種別を判定（`event` / `deadline` / `homework` / `bring`） |
| FR-2.4 | **4分岐で判定する**（下記） |
| FR-2.5 | 取り込み単位に**「版」**を持たせ、「この年間予定表から入れた予定はこの18件」を保持 |
| FR-2.6 | 改定版をアップロードすると、**変わった件だけ**一覧で出してまとめて差し替え |

**FR-2.4 の4分岐**

| 判定 | 条件 | 扱い |
|---|---|---|
| **完全一致** | 同じ子・同じ日・同じ内容 | **黙ってスキップ。承認を出さない**（記録だけ残す） |
| **差分あり** | 同じ日で詳細が増えている | **追記候補**として、増えた部分だけ見せる |
| **日程変更** | 似たタイトルで**日付が違う**（前後2〜3週間） | **変更候補**。旧→新を並べる。書き換えは承認必須 |
| **新規** | 上記以外 | 通常の登録候補 |

| ID | 要件 |
|---|---|
| FR-3.1 | エージェントは候補を返して止まる。書き込みは承認後（P2） |
| FR-3.2 | 承認された予定を Google カレンダーに登録（P6） |
| FR-3.3 | `/kid` から来たものも `/board` の「承認まち」を通す |

### FR-4 今日やること（`/kid`）

| ID | 要件 |
|---|---|
| FR-4.1 | 予定・定期・単発・配分された分を**1本のリスト**で出す |
| FR-4.2 | 初回に見えるのは「**今日やること3〜5個**」だけ。グラフ・統計は2階層目 |
| FR-4.3 | 共用端末では**名前を選ぶだけ**で切り替わる（PINなし） |
| FR-4.4 | 完了操作は**1タップ**。低学年は読み書きゼロで完結 |

### FR-5 タスクの3分類

| 種類 | 例 | 入口 | 見届け方 |
|---|---|---|---|
| **定期** | 公文の毎日プリント | **テンプレート。入力なし** | 毎日自動で並ぶ → チェック |
| **単発** | 学校の宿題、提出物、持ち物 | 学校PCの画面を撮る／手入力／言う | その日のリストに出す |
| **分割** | 塾の範囲課題、テスト勉強 | 範囲と締切を渡す | 枠に配る／触れる／組み直す |

**公文は内容が日替わりでないため、撮る必要も打つ必要もない。下の子の入力問題はこれだけでほぼ消える。**

### FR-6 学習スケジュール（上の子の本命）

| ID | 要件 | 根拠 |
|---|---|---|
| FR-6.1 | 枠は「**表示は量、内部は時間**」の二層 | 量で書かないと達成判定が曖昧、時間がないと教科をまたいで合算できない |
| FR-6.2 | 所要時間は**既定値＋実績で自動補正**。初期入力ゼロ | 9教科ぶん聞くのは入力が重すぎる |
| FR-6.3 | 枠は**曜日ごとに1回登録**（当日上書き可） | 「動かせない時間を先に引いた残り」が枠 |
| FR-6.4 | 配分は均等割りではなく**前倒し**を初期値に | パーキンソンの法則。緩い量に実績が張り付く |
| FR-6.5 | **収まらない場合は「入りません」と明示** | *最大の価値。* 人間は前日の夜に気づく |
| FR-6.6 | 遅れは**計画線と実績線の乖離グラフ**で見せる | 文章の警告より線が開く絵が刺さる |
| FR-6.7 | **予備日を2週間に2〜3日**確保し、未完了は**予備日へ送る** | 翌日に雪崩れると自己嫌悪→離脱の連鎖 |
| FR-6.8 | 削る対象と着手順は**提案するが、決めるのは本人** | P3。既存アプリが空けている差別化点 |
| FR-6.9 | 計画は**下書き**で、本人が触れる | 渡された計画は守られない（P8） |
| FR-6.10 | 触った瞬間に再計算され、結果がその場で見える | 自分で調整できるようになる |
| FR-6.11 | 「元に戻す」を常に置く | 触るのが怖いと触らなくなる |
| FR-6.12 | 範囲の追加・変更→再生成が初回と同じ軽さ | 範囲発表は直前かつ変更される |
| FR-6.13 | 未完了は消さない（週次リセットをしない） | 消えると「終わらない」に気づけない |
| FR-6.14 | テスト◯日前にテスト期間モードへ切り替え | 通常の宿題より配分を優先する |

| ID | 要件 |

| FR-7.2 | 付与は自動。**取り消しは日常の導線に置かない**（下記） |
| FR-7.12 | 親が**理由つきで増減を1行足せる**（調整）。マイナスのリセット・臨時の加点・訂正をこれ1つで賄う |

| FR-7.11 | 親が**スタンプ1タップ**で反応でき、書きたいときだけ一言添える |

**配点（実装済み・変更するときは要相談）**

| 種別 | pt |
|---|---|
| 宿題 | 3 |
| 提出物 | 3 |
| 持ち物 | 2 |
| 行事 | 0 |
| **テストの直し** | **直した問題1つにつき 1** |

**取り消し（revoke）を親の日常操作にしない。**

親が子のポイントを取り消すのは、子から見れば「**疑われた**」体験になる。
解こうとしているのは「漏れる→怒られる→子が自信をなくす」の連鎖なので、
ここでアプリが疑う役を引き受けると、**怒る役をアプリに移しただけ**になる（P8）。

ズルへの対応は、**引き換えの承認のときに人が話せばよい**（FR-8.6）。
アプリは記録するだけで、判定しない。`revoke` は入力ミスの訂正のために残すだけの口で、
`/board` の日常導線には出さない。

**代わりに「調整」を置く。** 親が理由つきで増減を1行足せるようにしておけば、
残高がマイナスになったときのリセットも、「これもやったらポイントあげよう」という
臨時の加点も、数え間違いの訂正も、**ルールを増やさずに**扱える。
調整は理由とともに台帳に残るので、あとから経緯を辿れる。

**ルールを先に全部決めきらず、走らせながら家族で相談して直していく。**
そのための口が「調整」である。

**テストは点数ではなく「直した数」に付ける。**
→ **点が悪いテストほどポイントが取れるので、隠す動機が消える。**

### FR-10 相棒の会話

#### FR-10.1 態度ルール（実装済み・変更しない）

`mimamori/kid_agent.py` の instruction に実装されている。**UIの文言もこれに合わせる。**

- **答えを言わない。** ヒントは「場所」と「やり方」まで
- **残りではなく、済んだ数を数える。** 「あと3つ」ではなく「**1つ終わったね**」
  - 数を聞かれたら黙って話を変えず、「数は数えないことにしてる」と一度だけ言って次の1つを示す
- **評価しない。** 「えらい」「すごい」ではなく「**終わったね**」
- **責めない。** 期限を過ぎていても「まだ残ってる。今日やっちゃう？」
- **質問は1つずつ。同じことは2回まで**（3回目は引く）
- **前と同じ文を返さない**
- **秘密を持たない。** 親も見られることを画面に常時表示

**根拠**：解こうとしているのは「漏れる→怒られる→子が自信をなくす」の連鎖。
ここで催促を強めると、**怒る役をアプリに移しただけ**になる（P8）。

このルールは**相棒に対するもので、親には適用しない。** 称賛は人が担い、アプリは記録と提示に徹する。

#### FR-10.2 聞くことの3層（実装済み）

1. **今日のもの**（期限が今日以前）— 「宿題終わった？」
2. **明日の持ち物**（明日の `bring` / `event`）— 「明日の忘れ物ない？」
3. **先回り**（3〜7日先の行事・テスト・提出）— 「週末◯◯だけど、進んでる？」

**3つ目が伴走の核。** 言われなくても自分で気づいて聞く。ただし**1回の会話で1つだけ**。

#### FR-10.3 その他

| ID | 要件 |
|---|---|
| FR-10.4 | 雑談は受けるが、**2往復で今日やることに戻す** |
| FR-10.5 | 音声は読み上げではなく**双方向の会話**。v1 はテキスト、v2 で音声 |
| FR-10.6 | 相棒の性格は「げんき」タイプ（子どもが選択）。**口調のみで、内容は FR-10.1 が優先** |

## 10. アーキテクチャ

### 10.1 構成

ADK（`LlmAgent` + ツール）／ Vertex AI Gemini ／ Google Calendar API ／ Firestore ／ Cloud Storage ／ FastAPI ／ Cloud Run ／ LINE Messaging API。
画面は `/`（撮る）・`/kid`（伴走）・`/board`（親）・`/reward`（引き換え）。

### 10.2 エージェント

| エージェント | ツール | 自律／承認 |
|---|---|---|
| `intake_agent` | なし（Gemini のマルチモーダル） | 読み取りは自律 |
| `schedule_agent` | `list_events`（自律）／`insert_event`・`update_event`（承認後） | 完全一致のスキップは承認不要 |
| `plan_agent` | `parse_scope`（LLM）／`propose_plan`（**コードの配分ロジック**） | 下書きまで。確定は本人 |
| `coach_agent`（kid_agent） | `get_my_tasks`, `start_task`, `finish_task`, `get_points`, `request_redeem`, `send_message` | 完了マークまで自律、引き換えは申請止まり |

**`coach_agent` は毎回 `get_my_tasks` を呼んでから返事を書く**（記憶が残らないため、思い込みで話さない）。
**計画の触り直しはエージェントを経由しない**（クライアント＋配分ロジックで即時反映）。

### 10.3 LLM とコードの分担

| | 担当 |
|---|---|
| **LLM（Gemini）** | 範囲の読み取り、種別・日付の正規化、重複／変更の候補判定、「入りません」の説明、会話 |
| **コード** | 枠への配分、再計算、締切超過の検出、残量の集計、見積もりの補正 |

## 12. 将来構想 — 相棒の身体（ロボット）

相棒キャラを卓上ロボットで実体化する構想。**版には置かない**が、設計の前提としてだけ残す。

**候補**：自作スタックチャン（約1.2〜1.5万円・カメラなし）／公式スタックチャン（組立済・カメラ付）／Reachy Mini（Lite $299・外部PC必須／Wireless $449・単体動作）

**常時稼働のデスクトップを導入予定**のため、**外部PCが必要な Lite が選択肢になる**。

**構成の見立て**：公式 Conversation アプリ＋自作ツール追加で、ツールを `get_my_tasks` / `finish_task` / `get_points` に差し替えて `coach_agent` の身体にする。シミュレータがあるので**買う前に検証できる**。

**原則との整合**：ロボ側は読み取りと完了マークまで自律、引き換え・送信は既存の承認フロー（P2）。カメラは「気づく」までで、録画・監視には使わない（P8）。

**順路**：Cloud Run に `coach_agent` のAPIを先に立て、ガワは後から選ぶ。**中身が先、身体は予算が許すとき。**
